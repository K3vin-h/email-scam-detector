# Django Backend

## Data model (`dashboard/models.py`)

**`EmailRecord`** — one row per scanned Gmail message, keyed by `gmail_id` (unique) to make scans idempotent.

| Field | Type | Notes |
|---|---|---|
| `sender`, `subject`, `snippet` | `CharField`/`TextField` | Raw email metadata |
| `received_at` | `DateTimeField` | From Gmail's `internalDate` |
| `confidence` | `FloatField` | Raw model output, 0.0–1.0 |
| `is_scam` | `BooleanField` | Risk-adjusted flag (see [03-scanning-and-risk.md](03-scanning-and-risk.md)) — not the model's raw threshold check |
| `labeled_in_gmail` | `BooleanField` | Idempotency flag for label application |
| `reasons` | `JSONField` | Rule-based tags, computed at scan time |
| `user_risk_override` | `CharField`, choices | Manual correction; empty string = no override |

`risk_level`/`risk_label` are deliberately **not** columns — they're computed at serialization time from `confidence`, `is_scam`, and `user_risk_override`. This trades query-time cost (see [07-limitations.md](07-limitations.md)) for the property that changing the risk-classification rules never requires a backfill migration.

**`ScanSettings`** — singleton row (`save()` forces `pk=1`); global configuration for scan window, scan frequency, and notification settings.

**`SummaryReport`** — periodic snapshot (`daily`/`weekly`/`monthly`) of scam counts and top senders, regenerated by `dashboard/reports.py`.

## Serialization layer (`dashboard/serializers.py`)

`EmailRecordSerializer` exposes `risk_level`/`risk_label` as `SerializerMethodField`s backed by `risk_level_for_email()` — every serialization recomputes risk from current data and current rules.

`ScanSettingsSerializer` enforces range validation (`scan_window_days` ∈ [1, 365], `scan_frequency_hours` ∈ [1, 168]) and a cross-field constraint: `notify_email_address` becomes required when `notify_via_email=True`. This is server-side validation independent of whatever the frontend form already checks.

## API surface (`dashboard/urls.py`, `dashboard/views.py`)

| Method & path | View | Notes |
|---|---|---|
| `GET /api/health/` | `HealthView` | Unauthenticated |
| `GET /api/emails/` | `EmailListView` | `?is_scam=`, `?risk_level=` filters; paginated |
| `PATCH /api/emails/<id>/risk/` | `EmailRiskFeedbackView` | Manual correction; invalidates cached reports |
| `GET`/`PATCH /api/settings/` | `ScanSettingsView` | Includes live Gmail connection metadata |
| `GET /api/reports/` | `SummaryReportListView` | `?period=` filter; lazily backfills on first read |
| `GET /api/stats/` | `StatsView` | Aggregate totals |
| `GET /api/stats/daily/` | `DailyStatsView` | 7-day scan/scam series |
| `GET /api/stats/senders/` | `TopSendersView` | Most impersonated domain, highest-risk sender, trend % |
| `POST /api/scan/` | `ScanView` | Synchronous on-demand scan |

All routes except `/api/health/` require `IsAuthenticated` (Django session auth). Throttling is configured globally in `core/settings.py` (`AnonRateThrottle`, `UserRateThrottle`).

## Risk-level filtering cost

`EmailListView`, `StatsView`, `DailyStatsView`, and `TopSendersView` each filter by computed risk level via a Python-side loop over the full `EmailRecord` table, then constrain the queryset with `id__in=[...]`. This is O(n) per request rather than a database-level predicate. Acceptable at current scale; flagged in [07-limitations.md](07-limitations.md) as the first thing to change if row counts grow substantially.

## `EmailRiskFeedbackView` request lifecycle

1. Validate `risk_level` against the allowed set (400 on failure).
2. Look up `EmailRecord` by primary key (404 on miss).
3. Persist `user_risk_override` with `update_fields` scoped to that column.
4. Invalidate and regenerate `SummaryReport` rows so aggregate totals reflect the correction immediately rather than on the next scheduled report job.
5. Return the record, re-serialized.
